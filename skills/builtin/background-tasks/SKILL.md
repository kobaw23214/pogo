# 后台任务

使用当前会话的 `background_task` 工具完成后台委托。Skill 提供操作方法，
宿主负责持久化、调度、队列、截止时间和审批。来源接入与业务判断由 Agent
按用户授权编写，不限于某几种预定义事件源。

管理员在 Agent 配置中勾选本内置 Skill，会联动启用 `background_task`，
取消勾选则一并停用；工具行展示关联关系，不能单独勾选。旧配置中的 `watch`、
`watch_test` 保留兼容，但不能将其局部权限视为完整的 `background_task` 授权。
`watch_decide` 由宿主仅在真实哨兵事件处理上下文中提供，不是普通聊天的等待工具。

## 选择执行方式

| 用户目标 | 选择 |
|---|---|
| 指定时间执行一次；每天生成报告；每个周期都完成一次任务或保存采样，即使数值不变 | `source: schedule` |
| 用脚本持续观察，只在业务条件成立、出现新事件或变化时唤醒 Agent | `source: sentinel` |

哨兵中，来源支持可靠订阅时可用 `mode: stream`；需要反复查询时用 `mode: poll`。
用户未指定轮询周期时，优先省略 `interval_seconds` 使用宿主默认值，
或根据来源负载与响应时效选择合理周期，并说明实际安排；不直接照搬示例频率。
不要为了显得“异步”额外建立 shell 常驻进程、cron 或前台等待循环。
用户已指定的采样和报告语义优先，不把“每次都保存”改成“变化才保存”。

先确定任务目标、来源范围、触发节奏、停止条件和需保存的结果。已有信息足够
就直接执行；只有缺少必要参数或授权范围不明确时才询问。读取或引用此 Skill
文档不授予权限，配置关联也不增加网络或外部写入权限。缺少 `background_task`
时说明需要有权用户在 Agent 配置中启用本 Skill，不用脚本绕过；写脚本仍须有
相应的文件工具权限。

## 定时任务

`task` 只描述**触发一次时完成的工作**，时间安排和生命周期放在独立字段。
不要把“创建定时任务”“循环十分钟”“到期停止”再写入每次执行的指令。
例如，用户要求每两分钟统计一次目录，十分钟后停止，且已授权开启：

```json
{"action":"create","source":"schedule","title":"目录文件统计","task":"统计工作区 testdir 目录当前的文件数，返回采样时间和文件数量；本次读取失败时明确报告失败。","kind":"every","every_seconds":120,"timezone":"Asia/Shanghai","stop_after_seconds":600,"enabled":true}
```

示例中的目录、时区和时间应替换为实际请求。其他时间方式使用 `kind: at`
与 `at`，或 `kind: cron` 与 `cron`；时区使用明确的 IANA 名称。
`every` 首次执行在完整间隔之后；截止时刻不再接纳新运行，不承诺固定成功次数。
宿主自动保存每次执行的结果和记录；定时任务不调用 `watch_decide`。

## 脚本哨兵

先读 [references/sentinel-scripts.md](references/sentinel-scripts.md)，再完成
`prepare → 编写业务代码 → check → create`。它们都是同一个 `background_task`
入口的操作；不再另建一套执行路径。

- `prepare` 安装受控协议 SDK 和未实现的入口模板，不会注册或开启任务。
- `check` 是有界**试运行脚本**，会访问脚本接入的真实来源，仍受权限和审批
  约束；它不提交正式进度、不注册任务，也不唤醒处理 Agent。
- 检查回执的实际验证范围。收到合法协议帧不等于业务条件、完整 ACK 循环或
  长期可靠性均已验证。静默来源超时属于未验证，不能报告检查通过。
- 检查失败或 `verification: unverified` 时先排查并有依据地修正，不继续 `create`。
  取得合法帧并核对实际观察范围后再注册；不强行等待真实业务事件发生。
- 正式 `create` 指明长期目标、脚本、运行方式和用户要求的生命周期。

## 开启、管理与结束当前委托

只有用户要求启动后台运行时才传 `enabled: true`；只要求准备方案或脚本时
不要开启。`create` 默认暂停。用户限制运行时长时，传 `stop_after_seconds`
或 RFC3339 `expires_at` 二者之一；单次 `timeout_seconds` 不能代替任务期限。

成功注册后，按宿主回执说明任务 ID、已开启或暂停、节奏、下一次运行和截止
时间（以回执实际提供为准），并区分“已注册”与“首轮执行成功”。随后继续
用户的其他请求或结束当前回复，不 sleep、不轮询等待整个周期，也不保留一个
“等待后台完成”的前台 Todo。用户从主会话的“哨兵”入口或后台任务查看后续记录。

查询和管理使用返回的 `task_id` 与对应 `source`：`list`、`status`、`pause`、
`resume`、`remove`。暂停不承诺撤销正在执行的操作；移除保留执行历史。
恢复不会延长原截止时间，已到期任务需要用户明确的新运行安排。
状态和结果未知时先核对，不重复创建相同任务或盲目重放可能已有影响的操作。

哨兵中断批次可在核查已发生的影响后，按用户要求使用
`background_task {"action":"retry","source":"sentinel","task_id":"返回的任务 ID"}`
显式重试；这可能重新执行原操作。该动作不支持 `source:schedule`，也不是延长
任务期限或重建监听的入口。

哨兵被事件唤醒后，只处理宿主交付的当前批次，并在完成所需调查后调用
`watch_decide`：无需后续处理用 `ignore`，保存站内报告用 `report`，有待继续
的工作用 `defer`。报告不代表发送了外部通知；外部动作仍遵循原有授权和审批。
