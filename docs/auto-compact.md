# 自动压缩（auto-compact）：设计稿

状态：v1 已实现（本文件描述的范围），v2/v3 是留白不是承诺。
依据：`自动压缩-sota-调研报告-2026-08-30.md`（仓库根目录，42 轮调研）+ pi 上游 issue #92 + arXiv 2606.22528。

## 1. 为什么改了主意

`agent/compact.go` 头部的结论——压缩只手动——建立在不自动的两条理由上。这两条理由现在都有了新的证据，而结论可以收窄成一条：

1. **「问题形态未出现」**（本项目 100 份转录：大 session 88%–99% 是工具输出，机械清理可释放 90%–97%）。这条仍然成立，而且它论证的正是级联：清理（可逆）已经在第一级自动跑着，压缩（有损）只是它后面的第二级。真正的坑在清理也救不了的时候——上游 Codex 的 #24732 是一个 4350 次工具调用、43.5MB 转录的会话在「大到无法压缩」里僵尸了两小时；pogo 的 `EndContextOverflow → DispositionIntervene` 停在同一个位置，只是诚实得多：它报错，然后等人。
2. **「压缩丢约束」（arXiv 2606.22528：0%→30% 违规，中文 −42 点）**。这篇论文自己给出了把违规率恢复 0% 的解法（Constraint Pinning，约束隔离在有损摘要之外 verbatim 重注入），并且四种策略对比里 **head_tail（保留最老轮次）本身就是 0%**——pogo 的 `continuation()` 把首条用户消息原文钉进压缩产物，正是这个策略的骨架。风险没有被否认，它是参数和保留清单要回答的问题。

决定性的家谱证据：**pi 上游（issue #92，badlogic 本人设计）已实现自动压缩且默认开启**。pogo 是 pi 系里唯一还坚持纯手动的。SOTA 十二家的共识形状是：级联（可逆先行）+ 回合边界触发 + 强制保留清单 + 熔断 + 溢出恢复——不是「到点就摘要」。

## 2. v1 的范围（本文件实现的部分）

**一句话**：`-compact auto` 显式开启后，在**运行之间**（不是运行中间）由驱动层触发既有的 `Agent.Compact()`；上下文溢出时压缩一次并原文重放该条 prompt；连续 3 次失败熔断。手动 `/compact` 的语义一行不改。

### 2.1 为什么 v1 只在运行之间

技术上是因为持久化对账，不是因为谨慎的修辞：

- `TurnPersister` 与 end-of-run flush 按**消息数**对账（`persisted`、`recorded`）。运行中间改写历史，对账基准就没了。CLI 的 compact 闭包（`main.go`）已经有一套完整的「压缩 + `Fork("")` + `AppendAll` + 重置 `persisted`」——它成立的前提正是「此刻没有 run 在飞」。
- pi 在轮内（工具批后、下一响应前）压缩，是因为 pi 的会话文件以 CompactionEntry 记录压缩事件、加载器只应用最新一次。pogo 的会话文件是 append-only 树，等价物是 Fork——Fork 也能在轮内做，但那需要新的事件种类进 wire 契约（`loop.go:715-721` 对 force-clear 的那段论证原样适用于此）。这是一份独立的设计变更，放进 v2。
- 运行之间已经覆盖主要形态：pogo 自己的测量里，撑大的会话是**跨整个 session 长出来的**，不是单个 run 里。REPL 每条 prompt 前检查 = pi 的 "before each new user prompt"；chain 的每个 run 前检查；web 的每次 Start 前检查。

### 2.2 触发

```
compact.autoThreshold: contextTokens > contextWindow − max(16384, contextWindow/20)
```

- `-compact` 的取值：`off`（默认，即现状）、`auto`（上式）、`auto:80%`（百分比）、`auto:120000`（绝对 token 数）。
- 判定用 `promptTokens()`（实测基线+估算增量，见 `loop.go:300-333`），与上下文清理的判定同一个数——两套阈值各自猜一个数是 SOTA 里被 #28728 抓过的坑。
- 与清理的关系：阈值不保证清理先跑（清理是视图、按自己的 4/5 窗口触发），但溢出路径保证了——`forceClear`（可逆）先试，压缩只在可逆手段失败后发生（§2.3）。
- 默认 **opt-in**（与 pi 的默认 on 不同）。理由不是风险（v1 的自动路径与手动路径是同一段代码），而是 pogo 的已部署场景（malagent 无人值守）宁可行为不变也要显式声明。溢出恢复同样只在 `-compact` 非 off 时启用。

### 2.3 溢出恢复（把 Intervene 的最常见一支自动化）

run 以 `EndContextOverflow` 结束时（`forceClear` 已经救不了），若 `-compact` 非 off 且本次未重试过：

1. 调用与手动 `/compact` 同一个闭包（压缩、Fork、落盘、重置对账）；
2. **原文重放**同一条 prompt 开一个新 run——失败的那条 prompt 已被摘要收编，重放让它以原文回到锚点（opencode 的 replay-last-user-message 同款）；
3. 每条 prompt 至多重试一次；压缩返回 `ErrNothingToCompact`/`ErrNotSmaller`（单条 prompt 本身过大）时不重试，错误照旧上抛。

`EndContextOverflow` 的 `Disposition` 保持 `Intervene` 不变：处置表描述的是「无自动压缩时的正确动作」，自动压缩能用上的场合根本走不到表那里。

### 2.4 熔断

自动路径连续 3 次压缩失败 → 本进程内停用自动压缩并说明原因（Claude Code 同款；其动机数据：1279 个会话连续失败 50+ 次，每天浪费约 25 万次调用）。手动 `/compact` 不受熔断限制，成功一次即复位。

### 2.5 保留清单（v1 继承自手动路径）

首条用户消息 verbatim（`continuation()`，head_tail 骨架）+ 摘要提示词里的逐字引用约束 + 语言跟随。v1 不新增：尾部 20K 原文保留、`## Constraints & Preferences` 固定段、压缩后回读最近文件——见 v2。宿主持有的状态（已加载 Skill、最新任务清单、改过的文件、跑过的 shell 命令）已在 v2-d 中由宿主直接带过压缩，用户后续消息的原文在 v3-a 中带过压缩，手动和自动路径相同。

## 3. v2 / v3 留白

- **v2-a 尾部保留（keepRecent=20000）——已实现**：`Agent.CompactKeep(ctx, keep)` 由自动路径使用（手动 `/compact` 保持全摘要形态）。要点：①尾部从 assistant 消息处开始（配对完整 + continuation(user) 后保持交替，严格交替端点安全）；②两条消息的历史取全摘要形态——head 只剩问句时 continuation（钉住+框架）必然大于 head，`ErrNotSmaller` 恒拒绝，全摘要反而保住了原文钉住；③重复压缩经 `<previous-summary>` 锚定块继承并「更新而非重述」（pi/Pydantic/Hermes 共同约定）；④钉住抽取：第二次起 pin 只取 `<original_request>` 块，摘要不再逐轮堆叠（Codex `SUMMARY_PREFIX` 同一目的）。SOTA 依据：ConstraintRot head_tail 0% 违规、TRACE divergence 0.149 vs 0.233（保原文 < 折进摘要）、pi/omp/Codex 默认 20000。
- **v2-b 轮内触发**：需要 wire 契约新增事件（压缩在轮内发生），TurnPersister 与 flush 的对账改为事件驱动。pi 的检查点（工具批后、下一响应前）是目标形状；pi 自己的 #2871（轮内不检查 → 单轮膨胀到 400K 且静默恢复丢弃有效回复）是该缺口代价的实录——pogo 因清理在视图层逐调用兜底，单轮 prompt 增长已被约束，紧迫性低于 pi。
- **v2-c 溢出时先剪再压**：`summarise()` 已经摘要「清理后的视图」；失败路径可以再进一步——压缩调用自身溢出时返回清理版输入（对应 Codex #24732/#24388 的教训：后者的死锁正是保留的用户消息携带图片 base64，19.6MB 的压缩请求压不动自己）。
- **v2-d 压缩后状态回填（rehydration）——已实现**（`agent/compact_rehydrate.go`，手动和自动压缩共用）：摘要适合承载「发生了什么、为什么」，不适合承载宿主本来就逐字持有的四类状态，它们由宿主直接带过压缩：
  - ①**已加载的 Skill**：证据和 Skill 绑定工具组的加载判定相同（skill 原子、`/skill` 展开、对已注册 SKILL.md 的成功 read），推广到所有已注册 Skill。每个 Skill 成为续写消息里一个独立的 `InputSkill` 块。read 加载的 Skill 经 registry 的可信归属重新读取，按 `skills.Invocation` 格式写入；skill 原子按宿主载入的原文复制。单个 Skill 上限 20 KiB，合计 60 KiB，从最新的开始计入预算；超出的 Skill 改为一条“请重新加载”的路径指针，不截断规则文本。Skill 恢复后其绑定工具组保持声明（`agent-workflows` 压缩后不会被隐藏）。
  - ②**最新任务清单**：最后一次成功 todo 调用的完整列表（`tools.RenderTodos` 格式）。
  - ③**写过或改过的文件**：成功的 write/edit 路径，最新的在前，最多 20 个。
  - ④**跑过的 shell 命令**：头部里 bash 调用的命令原文和 workdir（按模型写的原样，不是解析后的绝对路径），每条一行：`- [exit 1] go test ./...`，有 workdir 时 `- [exit 0, in web/ui] npm test`。状态取自配对结果里的 `BashDetails`：退出码、`timed out`、`background`（后台任务的回执不是结果）；被杀或中止的、以及没有 details 的失败结果（如 workdir 被拒）记为 `failed`，没有 details 的成功结果记为 `ran`。最新的在前，同一命令加同一 workdir 只保留最近一次，最多 12 条。多行命令、超过 300 字节的命令和没有结果的调用不列：脚本不会被照着清单重跑，留给摘要描述。只带命令和退出状态，不从输出里提取错误码之类的细节，因为那做不到确定。要防的是摘要把命令记得“差不多”：少一个参数或换一个包路径的命令照样能跑，答的却是另一个问题。

  ②③④和指针放在 `</summary>` 之后的 `<restored_state>` 块里。尾部仍可见的状态不重复。连续压缩时，前一次 `<restored_state>` 中没被更新的状态继续带下去（按续写开头句识别，与 `previousSummary` 同样的防护）；恢复的 Skill 块本身就是 skill 原子，会被直接再次识别。摘要输入（`renderTranscript`）里 skill 原子只保留一行标记，钉住的原始请求里 skill 原子写成 `[Skill: 名称]`，避免同一份规则带两遍。若完整回填导致结果不比压缩前小，先退化为只保留指针，再退化为不回填，最后才由 `ErrNotSmaller` 判定。Claude Code 压缩后重新注入计划、最近文件和已调用 Skill，是同样的做法。
- **v3 约束钉住**：会话中用户明示的约束在摘要之外 verbatim 保留 + 压缩后自动断言存活（论文 conditional 检查：在→0%，丢→38%）。测试原语：`-compact-stress`（每次轮后强制压缩，Gemini `stressTestProfile` 同款）+ 100 份真实转录回放注入已知约束。
  - **v3-a 用户后续消息原文保留——已实现**（`laterRequests`，手动和自动压缩共用）：不从文本里“提取约束”，而是把用户说过的话整条带过去，因为约束就在用户的原话里，而用户文本只占大会话的 0.4%–0.9%。范围是钉住的首条请求之后、头部里用户发出的每条消息（直接输入、运行中插话、skill 原子写成标记），按时间顺序放进 `</original_request>` 之后的 `<user_messages>` 块。`[pogo]` 提醒、工具协议纠正、工具结果不算用户原话；尾部本身逐字保留，不重复。单条上限 4 KiB（超长的粘贴保留开头和结尾，中间写明省略字节数），合计 24 KiB，超出时丢最早的并写明省略条数。连续压缩时从上一份续写消息读回这些消息，再接上新的。若带上它们会让结果不变小，先于整体回填被丢弃，不会因此拒绝压缩。Codex 压缩时也从新到旧保留真实用户消息的原文；它的 [issue #45296](https://github.com/openai/codex/issues/45296) 记录了这种做法的反面：一次压缩保留了 192 条历史用户消息，其中少数超大消息占了绝大部分体积，压缩后的下一次请求仍有约 18.7 万输入 token。这里给单条消息也设上限，就是为了避开这个问题。
  - **还没做**：压缩后自动断言约束存活、真实转录回放。`TestStatedConstraintsSurviveRepeatedCompaction` 是确定性的 `-compact-stress`：每轮新增一条约束、每轮压缩一次、摘要模型故意丢掉所有约束，12 轮后每条约束仍逐字在上下文里。它证明的是“不依赖摘要质量”，不衡量摘要本身写得好不好；后者仍需要真实模型评测（评估报告 P1 第 4 项）。

## 4. 参数速查（v1 实际值）

| 参数 | 值 | 出处（调研报告 §5.6） |
|---|---|---|
| reserve | `max(16384, window/20)` | pi/omp 共识 16384 |

## 5. 测试

- `agent/autocompact_test.go`：`ParseCompactSpec` 全分支（off/auto/百分比/绝对值/非法值/无窗口）+ 阈值对窗口的缩放 + `ShouldCompact` 边界（阈值下/上、消息不足两条、off 时恒 false）。
- `promptTokens` 守卫回归：清理关、压缩开时它必须仍非零（原守卫「没人问就别走历史」的判据从「清理没问」改成「清理和压缩都没问」）。
- 根包驱动决策单测：溢出重试的守卫条件（enabled、未重试过、EndReason 匹配）与熔断计数。
- 既有 `compact_test.go` 全部不动即绿——手动路径零改动是 v1 的验收标准。
- `agent/compact_rehydrate_test.go`（v2-d，用真实内置 agent-workflows Skill）：首次压缩恢复 Skill 块、任务清单和改过的文件且工具组保持声明；连续压缩沿用上一份 `<restored_state>`、Skill 块不重复不变化、摘要输入只见标记；尾部已可见的状态不重复；恢复会让结果不变小时退化为指针；钉住的原始请求不含 skill 原子正文。v3-a：中途约束逐字带过压缩、提醒与首条请求不重复、闭合标签转义后能原样读回；预算按新到旧截断并写明省略条数，超长消息保留首尾；带上原话会导致不变小时先丢原话；确定性压力测试 12 轮后约束全部存活。shell 命令：状态取自 details（退出码、超时、后台、中止、无 details 的失败和成功），同一命令只留最近一次，多行和超长命令不列，带方括号和逗号的 workdir 与命令能原样读回；连续压缩沿用上一份命令列表、新一次运行的状态覆盖旧的、尾部可见的命令不重复；列表最多 12 条且保留最新的。
- `skills/catalog_size_test.go`：内置 Skill 目录段的体积上限（2026-11-01 实测 7 个 Skill、3666 字节，上限 3850）。
- `cmd/compact-eval`：真实模型的压缩质量评测（评估报告 P1 第 4 项）。固定一个约 4.4 万估算 token 的编码会话，5 条约束只出现在用户消息里，5 个事实只出现在工具输出和助手笔记里；用配置的模型压缩（`--rounds` 次，每轮之间追加不含新约束的后续工作），再由三个互不可见、不带工具的探针提问：列出全部约束、按约束写代码和提交信息、回忆事实。全部是确定性字符串检查，不用模型打分。密钥只从配置的 `key_env` 环境变量读取，写出的文件会抹掉密钥。在两个构建上各跑一次即可做 A/B。
  - 2026-11-01 用 GLM-5.3 跑过（证据在 `.ci-artifacts/compact-eval-20261101/`）：压缩 1 次和 3 次，改动前后的构建在约束和行为上都是满分，GLM 的摘要本身就保住了全部约束；连续压缩 3 次后，工具输出里的细节回忆从 30/30 降到 27/30（丢的是准确的测试命令和错误码的归属），两种构建都有。用户后续消息原文保留在这个模型上没有体现为分数差异，它防的是弱摘要模型。
  - 2026-11-01 加 shell 命令回填后再用 GLM-5.3 做了 A/B（证据和分析在 `.ci-artifacts/compact-eval-commands-20261101/ab-summary.md`；压缩 3 次，每边 4 次试验；夹具的 bash 结果改为带 `BashDetails`，非零退出记为错误结果，两边相同）：约束 20/20、行为 12/12、回忆 17/20，两边相同。不靠模型回答的确定性检查里，会话中 8 条单行命令逐字留在压缩后上下文里的，改动前 16/32，改动后 32/32。准确的测试命令这次两边都是 4/4，上一轮改动前丢过 2 次，现在它不再取决于摘要。代价是续写消息多 528 字符。改动后 error_code 少答对 1 次（3/4 → 2/4）：有两次答成了命令清单里的退出码 `1`。探针问的是“之前 go test 报出的错误码”，退出码按字面也算，所以这是歧义，不是信息丢失。
- `web/overhead_breakdown_test.go`：Studio 会话里手动压缩后续写消息带 Skill 块、分项仍含该工具组、重开会话视图一致、下一次请求带着恢复的 Skill 和工具。
