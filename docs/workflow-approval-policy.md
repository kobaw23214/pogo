# 工作流审批分配与禁止自批

本次在现有人工节点、Agent 结果审批、动作权限和统一 Run 之上增加可选审批策略。新建人工节点和新启用的 Agent 结果审批默认开启规则与禁止自批；旧节点未配置规则时保持原有语义，不重写历史文件或发布版本。

## 在管理页面配置

在节点配置中启用“审批分配规则”，选择“禁止发起人自批”，再选择分配方式：

| 方式 | 配置与行为 |
| --- | --- |
| 固定账号 | 从平台实际可用账号中选择候选。受理新 Run 时解析账号，排除禁止者、已停用和不存在账号，并自动授予本节点权限。 |
| 业务系统指定 | 业务后端根据组织或业务规则选择审批人，在接入凭据保护的换码请求中提供外部用户标识；Pogo 通过该入口的既有映射解析为平台账号。 |

固定规则示例：

```json
{
  "id": "review",
  "kind": "human",
  "prompt": "审核本次业务结果",
  "approval_policy": {
    "prevent_self_approval": true,
    "assignment": "fixed",
    "approvers": ["bob", "carol"]
  }
}
```

Agent 节点在 `approval:true` 时也可使用相同策略。无审批的 Agent 节点不能声明该规则。固定名单尚未选好时可保存草稿，但不能发布；启用规则需要发布新版本，既有 Run 仍沿用其原定义和分配快照。

多人分配沿用原来的单次人工决定：任一有权审批人先处理即可结束该节点，竞争决定只接受一次，不是会签。

## 禁止自批如何生效

- 受保护节点同时排除原运行办理人 `owner_id` 和本次实际发起人 `initiator_id`。显式重试时两者可能不同，均不能自批。
- 按解析后的平台主体 ID 判断，多个外部标识映射到同一平台账号不能绕过。
- 规则先于管理员、运行所有者及显式权限的快捷授权。受保护节点需要当前明确的审批授权，管理员身份也不自动产生审批权。
- 人工参与者管理不能给禁止自批者授予该节点审批权限。它仍可管理参与者、查看、取消或重试，具体由原权限决定。
- 审批命令在中央受理时再次读取原运行状态与目录授权，直接调用接口、旧页面或内部非超时调用同样检查。
- 系统超时仍按节点原先的拒绝/失败策略处理，不冒充人工审批。

原定义没有 `approval_policy` 时保持兼容，包括原所有者/管理员行为。要对现有流程启用保护，需明确配置并发布新版本；历史运行不会被事后改成另一套审批规则。

## 自动分配和运行记录

新 Run 的候选名单、最初有效分配与运行受理、首段队列及节点授权在同一 SQLite 事务中保存。无合格人时明确拒绝新运行，不开始执行，不兜底发起人或管理员。

自动分配仅授予对应节点的 `run.read`、`approval.decide` 和 `artifact.read`。不会增加流程编辑、启动、取消、重试或其他运行权限；业务单与发布入口范围仍逐请求检查。

管理页和嵌入页显示当前有效审批人、必要时的最初审批人及不能审批的原因。节点级审阅者只看到其有权节点的分配信息，其他节点名单和材料仍被裁剪。

具备原参与者管理权限的人可给其他非自批账号人工授权或撤回，当前审批能力取决于这些实时授权。固定名单用于自动初始分配，并不禁止原授权管理者调整其他审批人；最初分配快照仍保留。若全部审批人后来停用或授权被撤回，运行继续待处理，页面明确提示；由有权管理者分配其他合格账号，不自动换成发起人。

重启不重新分配或重放审批，保留同一 Run、已持久分配和原决定审计。显式重试创建新 Run，保留原候选名单与来源，再根据本次发起人和当前账号可用性重新筛选；没有合格人时拒绝重试。人工临时追加的审批人不会自动改变原候选快照。

重复提交同一启动或重试请求键时，已受理意图复用原分配回执，即使候选随后停用也能找回原 Run；改变定义、输入、发起身份或业务审批候选仍产生冲突。

## 业务系统指定审批人

节点配置：

```json
"approval_policy": {
  "prevent_self_approval": true,
  "assignment": "business"
}
```

业务后端在首次办理的授权请求中提供：

```http
POST /api/workflow-embed/publications/{publication_id}/launch
Authorization: Bearer <业务后端保存的接入密钥>
Content-Type: application/json

{
  "subject": "employee-a",
  "origin": "https://business.example.com",
  "business_id": "tenant01:order:12345",
  "inputs": {"order_id": "12345"},
  "approver_subjects": {
    "review": ["employee-b", "employee-c"]
  }
}
```

`review` 必须是该入口固定版本中声明业务分配的审批节点。每个外部标识必须已配置为该入口中的普通平台账号映射；每节点最多 50 人。未知节点、固定分配节点、未知映射或无效名单明确拒绝。

映射结果绑定到服务端启动码与短会话，不经浏览器转成账号权限。浏览器 `inputs` 或 `POST /runs` 中自行增加的审批人字段不会取得分配权；单有访问会话也不能补出业务审批候选。缺少合格分配时，启动新 Run 返回明确错误。

恢复已有 Run 时提交 `run_id`，不重新提交审批名单；原分配由 Run 记录和实时授权决定。这样审批账号后续停用不会因为一份过期的分配名单阻止原发起人查看历史。需要新的业务分配时，业务后端应根据当前规则重新申请新办理授权。

业务系统负责从已验证身份和组织数据确定审批名单，例如部门负责人或业务角色；Pogo 当前提供固定账号和可信业务名单两种分配方式，不自行推断部门关系。

## API 与存储

- `GET /api/manage/workflows/{wid}/approval-subjects`：工作流编辑权限者读取可用账号的 `username`、`display_name`、`principal_id`，不返回凭据。
- 工作流保存/发布沿原接口，节点可选增加 `approval_policy`；保存回执保持发布指针、差异状态及当前权限，避免保存审批草稿后误显示未发布。
- 原 Run 查询增加请求投影 `approvals`：按节点返回 `prevent_self_approval`、`assignment`、`assignees`、`initial_assignees` 与 `blocked_reason`；它们只用于显示，不作为客户端授权依据。
- 运行目录元数据 `approvals` 保存原候选和分配，原 `workflow_run_grants` 保存实时节点权限；原 `run.json`、人工决定中的审批人/时间及执行段关联保持原机制。
- 原参与者、人工续跑、定时和任务中心控制接口继续使用同一分配与权限检查，业务单隔离和后台可靠回调继续生效。

## 独立本地验证

UI 夹具新增 `POGO_WORKFLOW_UI_STAGE4=1`，使用独立账号、流程、历史、SQLite 和本地脚本模型。默认固定候选为 Alice 与 Bob，Alice 发起后自动排除 Alice、分配 Bob；设置 `POGO_WORKFLOW_UI_APPROVAL_MODE=business` 时由独立业务后端提供映射到 Bob 的可信名单。夹具仍支持 A/B 单据隔离与本地回调接收器，不连接现有服务数据。

验收重点是：发起人按钮与直接接口均拒自批、管理员不绕过、Bob 无人工补授权即可审批、节点材料范围正确、重启后同 Run 续跑、无合格人拒绝、别名和浏览器名单不提权、重试与定时不绕过、旧定义/历史保持兼容。未部署 Docker。
