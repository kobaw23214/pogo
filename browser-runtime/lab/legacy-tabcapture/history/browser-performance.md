# 浏览器交互性能

Docker 浏览器继续由同一个远端 Chromium Page 执行。画面使用原生标签页采集和 WebRTC；用户无需安装扩展。用户输入使用绑定当前标签、页面代际和接管凭据的 WebSocket。

## 显示模式

默认保持「标准」模式，由浏览器按原有编解码能力协商。当前标签页的更多菜单可选择「响应优先」：在双方支持时优先使用 H.264，保留其它编码格式回退。它适合画面变化较多、发送排队明显的网页，并不保证所有页面更快；当前 ARM64 软件编码测试中，普通悬停和慢脚本页面也可能增加耗时。实际编码格式以连接信息为准。

显示偏好只影响当前标签页的 WebRTC 视频连接，browser-use、页面、登录状态、接管权限及原站布局不变。切换必须等已接受的输入和按键释放确认完成，再重建媒体并保留上一帧；当前新画面呈现前不恢复输入。只读查看时切换不会自动接管。旧服务未声明该能力时保持标准模式。分辨率、文字模式、码率上限、CPU 配额和原有帧率自适应策略均保持原设置。

## 连接信息

浏览器右上角菜单的「连接信息」按需显示测量结果。仅在页面和面板可见时采样客户端视频统计；服务端在新客户端显式请求后发送汇总。旧客户端不会收到不认识的诊断消息。

- 输入确认 P50/P95：客户端实际发送到服务端完成输入并回 ACK，不包含视频返回。
- 本地输入排队、服务端排队和执行：分别计时，不能把 ACK 当成可见反馈。连接信息同时展示未发送输入和在途请求数量；队列短不代表视频返回也快。
- 视频：实际帧率、码率、像素尺寸、网络 RTT、接收缓冲、解码和编码耗时。尚无样本时显示未知。
- 接管到可操作：从接管请求开始，到当前页面完成视频呈现且输入权限就绪。视频协商到首帧：从当前视频协商开始，到该视频首次实际呈现，不含空白页停留和网页加载时间；旧画面不能完成测量。
- 统计只包含计数、耗时和传输类型，不包含页面文字、输入内容、Cookie、SDP 或候选地址。

## 滚轮与生命周期

鼠标、滚轮、按键和文本共享有界输入队列。空闲时立即发送，后续连续输入在有限在途窗口内派发；鼠标移动不会再绕过滚轮背压。窗口根据真实确认耗时与服务端处理耗时有界调整，普通滚轮额外限制为最多两个在途请求。

仅合并尚未发送、同页面权限和按钮/修饰键状态的连续悬停位置。拖动对相邻未发送轨迹进行有误差及跨度上限的直线简化，保留起拖采样、折返、转弯、终点和离散操作边界。同位置普通滚轮累加距离，方向、位置、修饰键与其它输入的顺序仍保留。不同位置的滚轮可能命中不同滚动容器，不能为了降低队列长度任意跨位置合并；交错滚动和移动时，慢网站仍可能产生可见等待。

按下状态直到相应抬起确认才释放；失焦或异常时不会因本地已收到抬起而遗漏远端清理。视口调整须等待已接收输入排空，不能丢掉尚未发送的文本或抬起事件。连接、页面或控制权变化时丢弃尚未发送的旧输入，不重放已发送操作。

控制权完成切换或 Chromium 确认文档变化后立即推送状态，不再额外等待 300ms 轮询。媒体内部页面与 CDP 附加并行初始化；已匹配的显示尺寸也不再额外等 160ms。真实文档、视口及权限变化仍建立新的接收代际，并等待当前画面呈现后才允许输入。

短暂 ICE 中断保留一个有界恢复窗口。中断时停止输入，撤销待执行操作并释放按键；恢复后还必须呈现当前视频。失败或超时按原恢复路径重新连接。

## 自适应画质

编码尺寸与 CSS 布局不随负载变化，避免拖动过程中缩放及坐标错位。阅读和交互使用不同帧率上限，码率预算根据实际像素决定，并结合实测编码压力、发送排队及丢包调节。下降及时，恢复有滞后；低带宽估计本身不能把静态网页的码率不断压低。浏览器不支持某项调节时，保留现有可用视频。

VP8 编码在所有网络档位都最多使用 2 个线程。Chromium 默认按宿主机核数开到 8 个，在 worker 的 2 CPU 配额下造成周期性 CFS 节流，合成、采集和输入派发一起被暂停。受控测试中，连续滚动时被节流的周期从约 70% 降到约 15%，编码从约 14ms/帧降到约 9ms/帧；轻页面 hover 与拖动的尾部（3 次合并 p95）从 135–252ms 降到 118–135ms，p50 不变。「响应优先」使用单线程 H.264，不受影响。默认 CPU 配额仍为 2：提高到 4 只消除剩余节流，画面和输入没有可测改善；cpuset 反而更慢（见 browser-webrtc.md「编码线程与 CPU」）。线程上限固定为 2，不随 `POGO_BROWSER_CPUS` 变化；提高配额只给多个观看者各自的编码器留出余量。性能只测过配额 2 / 4、采集最高 1728×2160；最大视口（采集 3456×2160）只做过单次正确性检查，那时限制帧率和输入的是远端合成，不是编码。

远端显示密度默认是 1.5（此前为 2），由部署设置 `POGO_BROWSER_DEVICE_SCALE_FACTOR` 控制（`1`、`1.5` 或 `2`，见 browser-webrtc.md「远端显示密度」）。worker 每采集一帧都要按这个密度重绘整页并读回，DPR 2 下约 17ms，1.5 下约 14ms，是 worker CPU 中最大的一项。在 1280×1600 视口下 1.5 和 2 的编码尺寸相同。受控测试中，对高分屏观看者，1.5 让「标准」轻页面 hover 输入→可见 p50 从约 70ms 降到 35ms，滚轮从约 120ms 降到 67ms，CDP 派发从约 18ms 降到 1ms；文字清晰度为 2 的 0.94–1.07；代价是 ifeng 短滚动 capture→present p95 高约 16–24ms，连续滚动没有改善。普通屏观看者的轻页面输入不变。要恢复以前的画面，设 `POGO_BROWSER_DEVICE_SCALE_FACTOR=2`。设为 `1` 时这一成本降到约 3.4ms，「响应优先」连续滚动从 4–7fps 升到 25–34fps，代价是高分屏上的文字更软，边缘梯度为 2 的 0.88–0.93。

网络档位 `lan`（advertise 地址是 loopback 的本机部署自动启用；私网部署需要显式设置，见 browser-webrtc.md「网络档位」）让 Chromium pacer 以 2.5 倍带宽估计排空、排队不超过 250ms，「标准」观看者每个媒体 epoch 的带宽估计从 8Mbps 起步、不低于 4Mbps。受控 loopback 测试中真实网页滚动的每包发送排队从约 0.4–1 秒降到约 3–104ms，帧龄 p95 从约 0.85–2.1 秒降到约 0.1–0.3 秒。私网、公网或未知网络默认保持 Chromium 默认值，滚动大帧仍可能排队数百毫秒。帧率和码率自适应规则不变：Chromium 对屏幕内容排队报告的质量限制原因是 none，而降低码率上限无法明显缩小接近 QP 上限的滚动帧，单独按排队降级在测试中没有缩短排队。

`lan` 档位默认还通过 RTP playout-delay 扩展请求观看端以 0 播放延迟显示：每帧解码后立即呈现，不再按抖动缓冲目标留存；`POGO_BROWSER_WEBRTC_PLAYOUT_DELAY=default` 可单独关闭。受控测试中，接收端留存（jitterBufferDelay 减去组帧时间）从每帧约 5–210ms 降到 0–2ms，接收→呈现 p50 降到 4–8ms；连续滚动停止后的 capture→present p50 从约 100–240ms 降到约 13ms。轻页面输入→可见 p95 只在与基线运行范围分开的用例上降低，约 15–50ms（「标准」拖动 119–135 → 103ms、滚轮+移动 85–86 → 53ms，「响应优先」悬停 119 → 87ms、滚轮 152 → 103ms）；「标准」悬停和滚轮的变化在运行间离散范围内。帧间隔方面，三段连续滚动合并的样本（每段不计第一个间隔）略好，但单次运行有变差：第 3 段 3 次中有 2 次输入期间帧间隔 p95 从 67ms 升到 100ms，单次最大 150–183ms（未启用 67–134ms），最大值来自每段滚动开始后的第一个帧间隔；仍低于 250ms 的冻结门槛，冻结次数不变。连续滚动的 capture→present p95 仍由发送端 pacer 残余排队决定，没有改善。网页端不设置 `jitterBufferTarget`。`wan` 档位默认保留抖动缓冲。

## 验证口径

受控测试分别记录滚轮首次可见反馈、最终位置可见反馈、连续滚动结束后的尾延迟、文本可见反馈、接管和切页首帧。远端实际滚动量必须等于客户端真实 WheelEvent 的滚动量，不能用测试工具请求值代替浏览器实际生成值。

本机自动化的「输入到解码视频像素」不等于用户物理输入到显示器，也不能代表线上网络。基线和候选使用相同测试脚本、窗口尺寸、站点及资源限制，性能采样期间不并发构建或运行重测试；正确性、稳定性和原数据保留必须同时通过。

连续指针验收分别测悬停、拖动、纯滚动和滚动与移动交错。正常页面与人工增加事件处理耗时的页面单独报告；后者用于暴露排队，不代表真实网站的固定延迟。统计从客户端实际 DOM 输入事件开始，到解码视频中的位置到达为止，保留未到达样本、完整轨迹反馈分布、停止后的追赶时间和画面间隔，不能只检查最终位置，也不能仅挑选成功送出的坐标计算延迟。当前专项证据位于 `.localagent/checks/browser-pointer-latency-20261010/`。
